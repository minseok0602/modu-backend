# I:EUM 자동 배치: 외부 호출과 트랜잭션 분리

이 문서는 2026-11-25 로컬 실험의 설계와 구현 범위를 기록한다. 측정 결과는 `REPORT.md`에 별도로 기록한다.

## 문제와 가설

기존 `RouteRecommendService.autoArrange`는 일정 조회, 날짜 배치, 경로 조회·저장, AI 호출, 추천 반영을 하나의 트랜잭션에서 수행한다. Kakao·AI 클라이언트는 `WebClient.block()`으로 응답을 기다린다.

- 자원 가설: 외부 응답을 기다리는 동안 실제 JDBC 커넥션도 점유된다면, 동시 요청이 커넥션 풀보다 많을 때 대기와 응답 지연이 증가한다.
- 정합성 요구: 외부 응답 도중 사용자가 수정한 일정을 이전 추천이 덮어쓰지 않는다. AI·경로 조회·검증·최종 저장이 실패하면 이번 추천의 날짜·순서·간선·새 캐시가 일부만 저장되지 않는다.
- `@Transactional`만으로 모든 동시 수정이 차단된다고 가정하지 않는다. 실제 provider 호출 시 트랜잭션 활성 여부와 Hikari active/pending을 측정한다.

## 구현한 처리 흐름

1. **짧은 조회 트랜잭션:** 소유자를 확인하고 일정 부모 행을 잠근다. 일정·관광지·기존 간선·캐시를 읽고 변경 버전과 원래 상태를 기록한다. 초기화된 일정 그래프를 detach한 후 커밋해 락과 커넥션을 반환한다.
2. **트랜잭션 밖:** 요청 전용 복사본에서 기존 날짜 배치 알고리즘을 실행한다. 기존 간선·공용 캐시를 먼저 사용하고, 없는 구간은 Kakao에서 조회한다. 후보 경로로 AI를 호출하고 노드 집합·날짜·순서·고정 시작/종료 조건을 검증한다. 이 단계는 DB를 변경하지 않는다.
3. **짧은 반영 트랜잭션:** 부모 행을 다시 잠그고 변경 버전과 원래 상태를 비교한다. 변경·삭제되었으면 HTTP 409로 거절한다. 그대로면 날짜·순서·누락 간선·새 캐시·버전을 함께 저장한다. 저장 실패 시 모두 롤백한다.

Kakao 경로는 AI 입력의 의존 데이터이므로 AI 호출보다 먼저 필요하다. 의존관계를 무시한 병렬 실행은 적용하지 않았다. 개선 대상은 외부 대기 중 DB 자원 보유 시간이며, `block()`을 기다리는 요청 스레드 자체는 남아 있다.

## 동시성 규칙

- 장소 추가·삭제·재배치, 일정 수정·삭제, 최종 추천 반영은 같은 일정 부모 행에 `PESSIMISTIC_WRITE` 락을 먼저 획득한다.
- `route_revision`은 부모 정보뿐 아니라 자식 노드 변경에도 증가한다. 부모의 `@Version`만 추가하고 자식 변경을 놓치는 설계를 피했다.
- 버전 확인과 쓰기는 같은 트랜잭션·락 안에서 수행한다. 확인 직후 다른 수정이 끼어드는 틈을 만들지 않는다.
- 순서를 바꿨다가 원래대로 돌린 경우도 버전이 달라지므로 오래된 추천을 거절한다.
- 서로 다른 일정이 동일한 관광지 쌍을 동시에 조회할 수 있다. 공용 캐시는 고유 키 기반의 `INSERT ... ON DUPLICATE KEY UPDATE`로 먼저 저장된 값을 유지한다. 중복 외부 호출 자체를 합치는 single-flight는 범위에 포함하지 않았다.
- `route_revision`은 JPA 스키마 갱신에서 기본값 0으로 추가된다. 수동 마이그레이션 환경에서는 `schedule`에 `route_revision BIGINT NOT NULL DEFAULT 0`을 먼저 추가한다.

## 호환성과 범위

직접 자동 배치 API는 외부 대기 중 트랜잭션을 유지하지 않는 새 흐름을 사용한다. 자연어 Tool Calling은 상위 트랜잭션에서 여러 변경을 수행할 수 있으므로, 그 안에서 호출될 때는 기존 트랜잭션에 참여하는 경로를 유지한다. 미커밋 변경을 놓치거나 기존 다단계 롤백을 부분 커밋으로 바꾸지 않기 위한 선택이다. **자연어 명령 전체의 커넥션 점유를 개선했다고 주장하지 않는다.**

새로 계산한 간선은 AI 입력에서 요청 내 음수 후보 ID를 사용하며 DB에 저장하지 않는다. 최종 API 응답은 저장된 실제 간선 ID로 만든다. 기존 서버 검증 외에 중복 노드와 중복/범위 밖 날짜도 거절한다.

외부 호출에는 설정 가능한 제한 시간을 추가했다. 기본값은 OpenAI 60초, Kakao 10초다. 실제 운영 지연 분포에 맞춘 조정은 별도 작업이다.

## 정합성 검증

- Kakao와 AI가 실제 HTTP를 호출할 때 트랜잭션이 비활성인지 확인.
- AI 대기 중 다른 트랜잭션에서 원래 배치·간선·캐시만 보이는지 확인.
- AI HTTP 오류·타임아웃·잘못된 결과, 두 번째 Kakao 호출 실패 시 추천 관련 상태 불변 확인.
- AI 대기 중 재정렬·날짜 이동·미배치 전환·장소 추가·삭제·일정 기간 수정·수정 후 되돌리기를 실제 서비스로 수행. 변경이 AI 종료 전에 완료되고, 추천은 409로 거절되며 최신 상태가 유지되는지 확인.
- 일정 삭제 중 추천, 같은 일정의 두 동시 추천, 서로 다른 일정의 동일 캐시 미스 검증.
- MySQL 트리거로 최종 Edge 저장 실패를 주입해, 먼저 수행한 캐시 INSERT와 노드·버전 변경도 롤백되는지 확인.
- 상위 트랜잭션 강제 실패 시 기존 자연어 명령 경로의 전체 롤백 계약 확인.
- 소유자 검사와 고정 시작·종료 조건 회귀 확인.

## 성능 실험

- 비교군: 원래 HEAD `4a6a4a2`의 `RouteRecommendService`를 실험 소스셋에 보관했다. 패키지·클래스 이름과 자동 Bean 등록만 바꾸었고 메서드 본문은 동일하다.
- 새 방식과 같은 DB, 같은 JVM, 같은 실제 클라이언트·HTTP Stub을 사용한다. Stub은 입력 노드를 그대로 유효한 JSON 응답으로 반환한다.
- 별도 MySQL 8.0 컨테이너, Hikari 최대 5개. 서비스 호출 지연을 측정하므로 인증·서블릿·HTTP API 서버의 오버헤드는 포함하지 않는다.
- 주 실험: 날짜가 지정되고 경로·캐시가 준비된 장소 3개. AI 지연 0/2/5초 × 동시 요청 1/5/10 × 각 3회 × 전후 2개 방식 = 54회. 요청마다 다른 일정을 사용한다.
- 보조 실험: 날짜 미지정·경로/캐시 없음, Kakao 구간별 100ms·AI 2초·동시 요청 5개 × 3회 × 전후 = 6회. 서로 다른 관광지 집합으로 캐시 충돌을 분리한다.
- 두 방식 각각 5회 워밍업을 제외한다. 반복별 실행 순서를 교차한다.
- Hikari active/pending을 10ms 간격으로 수집하고 실제 시간 간격으로 점유량을 적분한다. 10ms보다 짧은 피크·트랜잭션은 표본에서 누락될 수 있다.
- 트랜잭션 시간은 Spring 트랜잭션 시작 완료부터 리소스 정리 직전까지 별도로 계측한다. 커넥션 획득 전 대기는 서비스 지연에 포함되며 이 트랜잭션 시간에서는 제외된다.
- `summary.csv`는 반복별 성공/실패·서비스 p50/p95·active/pending·점유 적분·트랜잭션 시간·외부 호출 수를, `timeseries.csv`는 원시 시계열을 기록한다.
- 낮은 동시성의 p95는 표본 수가 작아 사실상 최대값이다. 각 반복을 모두 공개하고 운영 처리 한계나 일반적인 SLA로 확대 해석하지 않는다.

## 재현

프로젝트 `modu` 디렉터리에서:

```powershell
# 정합성만
.\scripts\run-route-experiment.ps1
# 정합성과 성능 매트릭스
.\scripts\run-route-experiment.ps1 -Performance
```

실험은 loopback의 전용 `ieum_experiment` DB에서만 실행되며 그 DB의 테이블을 생성·삭제한다. 기존 애플리케이션 설정·환경변수·실제 공급자 키는 읽지 않는다. 결과는 `build/route-experiment`, JUnit 보고서는 `build/reports/tests/routeExperiment`에 남는다. 스크립트가 시작한 컨테이너는 종료 시 중지한다.

## 남은 범위

외부 공급자의 실제 AI 품질·요금·네트워크 변동, 자연어 명령 전체의 트랜잭션 재설계, 운영 트래픽 한계, 캐시 만료 정책, 수동 삭제 후 새 인접 경로 확보 문제는 이번 성능 실험과 구분한다. 외부 HTTP 호출 자체는 DB 롤백으로 취소되지 않으므로, 충돌 시 이미 수행한 공급자 호출 비용은 남는다.
